# Kooyu 优化依据：Marvis 的工作结构与 Granola 的视觉风格

日期：2026-11-15。本文保留参考分析、信息架构与视觉规范的设计依据；本轮已实施的功能、截图和测试边界以 [跨端工作台实施与验收](kooyu-workbench-implementation-2026-11-15.md) 为准，不将全部建议自动视为已上线。

更新约束：用户明确要求保留 Kooyu 自己的品牌色调。本版撤回上一版黄绿、鼠尾草绿、粉蓝等替代配色建议；Granola 仅作为排版、留白、层次、形状和交互节奏的参考。此前生成的 `output/research/kooyu-marvis-granola-20261115/visual-direction.png` 为已被本次决定替代的探索稿，不作为实施依据。

## 1. 结论

建议把 Kooyu 的体验收敛成：**从对话交代工作，在项目中组织工作，随时查看过程，最后查看和验收成果。**

Marvis 提供的是组织这条链路的参考；用户给出的 Granola 图片提供的是轻量表面、舒展排版、清晰动作和渐进交互的参考。Kooyu 保留现有「灵动回环 · 日落珊瑚」品牌，以及已有深浅主题和主次动作语义，在此基础上改善页面比例和组件细节，同时保留多 harness、项目目录、权限审批、模型来源和执行状态的准确表达。

本轮主建议保留用户此前确定的四个底部入口「对话 / 用量 / 模型来源 / 设置」、首页项目分组及右上角收件箱。在此基础上补充任务、成果和执行详情的承接，不直接照搬 Marvis 的底部标签。若以后将“任务”提升为底部一级入口，应作为单独的导航改版决定，同时明确用量和模型来源的新位置。

## 3. Marvis 的实际结构

### 3.1 四个稳定入口，围绕“让助手做事”组织

公开实际界面底部为「对话 / 任务 / 技能 / 我的」。每项回答一个问题：我要交代什么、哪些工作会自动执行、助手能做什么、我的设备和偏好是什么。

| 区域 | 可见事实 | 对 Kooyu 有价值的原则 |
| --- | --- | --- |
| 对话首页 | 问候、少量可点击示例、底部任务输入框；顶部显示当前设备 | 先允许用户表达任务，再按需补上下文和能力；当前执行位置应容易发现 |
| 侧边抽屉 | 新建对话、办公室、产出物、最近对话；长按菜单提供置顶/重命名/删除 | 同一工作入口内组织会话与相关工作资料；常用操作靠近对象 |
| 对话过程 | 文本回答之外有工具执行中的摘要、完成反馈和文件卡片 | 工作过程可理解，产物可操作；避免把完整内部日志塞入正文 |
| 工作日志/产出物面板 | 在同一上下文中切换工作日志和产出物 | 看进展与看结果可以相邻，但它们是不同的信息视图 |
| 办公室 | 多执行者的状态、用量、对话明细及执行者说明 | 将运行情况、能力和成本关联起来，而不是仅展示数字 |
| 任务 | 自动任务列表、空态示例、新建表单；描述、重复规则、执行设备；详情可立即执行和暂停 | 自动任务应是可回看、可停止的对象，并能从任务返回执行对话 |
| 我的 | 我的技能、设备管理、通知与权限、帮助、关于 | 低频管理进入二级页；设备连接状态单独表达 |

“办公室”的拟人化工位是 Marvis 的表达方式。Kooyu 可转译为「执行概览」，用真实 harness、Host、任务和状态表达，不必复制 3D 办公室或虚构多个正在工作的代理。

### 3.2 最值得借鉴的四条链路

1. **提出任务 → 展示执行摘要 → 交付可下载文件。** 工具状态出现在对话附近，最终文件形成可操作对象，而不只是一句“完成了”。
2. **侧边会话 → 工作过程 / 产出物 → 回到同一对话。** 进入详情不应丢失项目、会话、滚动位置和输入草稿。
3. **自然语言提出定时需求 → 可见的自动任务对象 → 执行记录。** 对话是创建入口，任务页是持续管理与核对入口。
4. **在设备上下文中发起任务 → 查看设备 / 连接详情。** 执行位置是任务上下文，不必每次打开设置寻找。

### 3.3 不应直接复制的部分

- Marvis 的最近对话平铺不能代替 Kooyu 的项目分组；项目与目录是 Kooyu 的核心工作上下文。
- Marvis 顶部的工作日志/产出物按钮不能占用用户已指定的右上角收件箱。Kooyu 可将详情入口放在会话标题附近，收件箱始终处理通知。
- “任务”中的自动计划、正在执行的工作和输入框中的排队消息不能合并成一种对象。排队消息是一条尚未执行的输入；工作有目标与验收；自动计划有触发规则与运行记录。
- 截图中的角色名称不能直接映射为已安装 harness 或技能。真实能力、可用状态和支持范围必须来自 Host。
- Marvis 允许连接自身手机的表现，不意味着 Kooyu 手机会在本机运行桌面 harness。当前执行仍在已连接的 Host。

## 4. Kooyu 的结构完善建议

### 4.1 保留四个底栏，把工作链路嵌入对话与项目

```text
对话
├─ 顶部：当前电脑与连接状态 / 新建对话 / 收件箱
├─ 首页：全局主对话 + 按项目分组的会话
│  ├─ 项目行：展开 / 新建对话 / 项目操作
│  └─ 项目操作：重命名 / 选择电脑目录 / 工作记录 / 成果
├─ 工作记录：进行中 / 待验收 / 自动计划 / 历史
├─ 成果：按项目、对话、类型查找并预览
└─ 对话正文
   ├─ 输入：附件、harness、权限、模型、思考；沿用桌面发送逻辑
   ├─ 运行摘要：当前动作、执行者、耗时；点击展开过程
   ├─ 工作详情：目标 / 执行过程 / 成果 / 验证证据
   └─ 上下文动作：托管、授权、停止、创建项目

用量
├─ 总览与趋势
├─ 项目 / harness / 来源筛选
└─ 指标 → 具体对话和执行记录

模型来源
├─ 来源与连接状态
├─ 来源内模型
├─ 各 harness 的绑定与默认模型
└─ 验证连接 / 查看错误 / 配置详情

设置
├─ 一级：远程连接与已保存电脑
├─ 二级：外观与通用 / 执行引擎 / 通知 / 帮助与关于
└─ 会话托管：手动查看和管理入口；日常优先在主对话触发
```

工作记录和成果可在首页放一个安静的「工作」入口、在项目菜单中提供当前项目入口；不要再增加一排大型功能卡片挤压会话列表，也不要将“项目”重新变成独立底部页。

这里的「工作记录」是一层组织视图，不是新增后端任务类型。普通执行对话没有明确工作目标时仍正常聊天，不能强迫每条聊天都创建 Goal。

### 4.2 页面需要回答的问题

| 页面 | 首屏首先回答 | 信息展开方式 |
| --- | --- | --- |
| 首页 | 我在连接哪台电脑、有哪些项目、最近在做什么 | 项目分组默认简洁，已运行/等待回答采用文字状态；其它管理进项目菜单 |
| 新建对话 | 这次准备做什么、在哪个项目和目录中做 | 主输入优先；展示当前配置，次要字段进二级面板；目录通过浏览选择 |
| 已有对话 | 助手正在做什么、有没有事情需要我处理 | 一个简短运行摘要；工具细节折叠；询问与审批直接出现在对话内 |
| 工作详情 | 目标是什么、进展如何、结果是什么、验证做了什么 | 目标、过程、成果分区；明确区分正在运行、等待用户、待验收和验收完成 |
| 自动计划 | 下次何时执行、在哪台电脑上执行、上次是否成功 | 自然语言规则及下一次触发时间；详情再编辑时区、次数及预算边界 |
| 成果 | 可以拿到什么、来自哪里、是否已验收 | 文件名、类型、大小/摘要、所属项目与对话、预览/下载、验证状态 |
| 用量 | 消耗在哪里、是否接近预算 | 汇总 → 项目/harness/来源 → 具体执行；无法获得的数据明确标未知 |
| 模型来源 | 哪个 harness 在用哪个来源和模型、是否可用 | 来源列表与绑定概览分开；编辑表单按当前类型展开，避免同时出现所有协议字段 |
| 设置 | 连接是否正常、如何调整偏好 | 当前连接直接展示；其余逐项进入二级页面 |

### 4.3 对话中主动触发管理，详情页承接结果

用户已明确的行为继续保持：

- “在这个目录新建项目” → 全局主对话调用项目工具 → 必要确认 → 项目出现在首页。
- “用 Codex 处理这个项目” → 如缺项目创建执行会话的授权，主动触发授权请求 → 确认后执行。项目授权不回到设置表单。
- “跟进直到测试通过” → 解析目标、执行对话和边界 → 对话内确认托管 → 在会话/工作详情查看关系、暂停或撤销。
- harness 提问/权限请求 → 右上角收件箱提醒 → 进入对应对话 → 原生表单/审批 → 显示确认结果。
- “每个工作日 9 点检查构建” → 生成自动计划摘要，展示时区、设备、动作和边界 → 确认后生效 → 工作记录可追溯每次运行。

不要为了显得智能而跳过授权。自然语言入口负责降低操作成本，Host 继续承担范围检查、去重、授权及停止语义。

### 4.4 当前实现的可复用基础与补齐范围

| 领域 | 已有基础 | 本轮建议补齐 |
| --- | --- | --- |
| 项目与会话 | 分组首页、目录选择、共享输入区、收件箱、询问/审批 | 用统一页面上下文和导航目标串起项目、任务、成果，避免大量互不相关的弹层开关 |
| 目标与成果 | Android/iOS 已有目标详情、交付成果与验收入口；Host 有 goals/artifacts/files 接口 | 增加可发现的项目/全局聚合入口；将正文文件卡片与工作验收关联；以当前接口权限核对实际可读范围 |
| 过程查看 | 已有原生事件、工具轨迹和会话详情 | 对用户显示简短过程摘要；原始日志留在展开详情，不与模型回答混排 |
| 自动计划 | Host 有 automations，Web 工作中心已有计划相关界面 | 移动端承接列表、摘要、暂停、运行记录；先核查原生客户端允许的路由，不能直接照搬本机管理员接口 |
| 执行能力 | 已有 harness 注册、能力元数据、执行节点与应用连接 | 先展示真实可用能力；技能广场只作为后续方向，不能把模型列表或硬编码卡片当作技能系统 |
| 费用与限制 | 已有用量、预算及会话关联 | 从费用数据跳回具体工作，区分模型消耗、托管管理消耗、估算与未知 |
| 配置 | 模型来源页及 Host 连接管理已存在 | 改善默认摘要、字段层级、错误反馈；保留真实来源/模型/harness 对应关系 |

## 5. Granola 图片的视觉总结

### 5.1 这张图的风格来自组合关系

**暖纸色的安静底面 + 接近黑色的清晰文字和动作 + 轻盈的圆角白色元素 + 少量有机色彩。**

1. **日常底面温暖、低饱和。** 多张后续步骤使用微暖、略带灰绿的近白背景，区别于科技产品常用的冷白蓝灰。
2. **主按钮非常明确。** 底部黑色或炭黑色胶囊按钮是主要视觉锚点；次要动作退为文字或浅色控件。
3. **标题带编辑感。** 英文标题使用衬线气质、常规字重、舒展行距和克制字数；不是每页都依赖粗重无衬线大字。
4. **色彩主要服务引导。** 黄绿、粉蓝、粉紫大色面配合轻纹理和自然/抽象形态。后续表单退回浅纸色，避免连续多步都高刺激。
5. **列表项轻而紧凑。** 白色圆角行、左侧小图标或淡彩圆点、右侧选择状态；选中靠细描边等手段确认，不靠大面积强色。
6. **信息一次只推进一步。** 内容区与底部单一主动作形成稳定节奏。复杂产品能力没有一次性展开成参数面板。
7. **软不等于模糊。** 文字、按钮边缘、选择状态仍有对比。截图里的浅字或微小文字不能照抄为可访问性标准。

### 5.2 Kooyu 中的使用分工

| 场景 | 建议表达 |
| --- | --- |
| 首次连接与产品介绍 | 使用 Kooyu 的珊瑚、桃色及其低饱和派生表面组织构图；每步一个目标，如连接电脑、选择初始偏好、开启提醒 |
| 首页与项目列表 | 沿用现有中性背景；紧凑分组列表；选中行使用现有选中态，品牌强调采用珊瑚体系，不给每个会话单独加厚边框和大阴影 |
| 新建对话欢迎页 | 可以保留一个安静的品牌焦点、短标题及极少量任务建议；避免品牌图、光晕、卡片、描边同时叠加 |
| 正在进行的对话 | 大面积保持安静；回答优先阅读；弱化气泡边框；把彩色留给状态、附件类型和必要选中态 |
| 权限审批 / 问题回答 | 使用统一表面、圆角与字体，明确展示对象、动作和范围；允许、拒绝同样容易找到；危险、警告、成功保留独立语义色，不能全部染成品牌色 |
| 模型与设置 | 成组列表 + 二级表单；减少大标题、厚卡片和密集框线；保留连接状态与错误的可读性 |
| 桌面端 | 使用同一品牌和语义主题规则，保留侧栏与阅读密度；移动端映射相同状态与层次，按触摸设备调整尺寸 |

保留 Kooyu 自己的标志、名称和品牌色调。珊瑚色用于品牌识别及当前设计中约定的强调，不借此把所有主按钮、所有状态统一改色；现有中性主动作也无需机械改成珊瑚色。不要复制 Granola 的 Logo、照片或受保护的图形。

### 5.3 保留品牌色，复用现有主题语义

品牌依据为仓库 `brand/design-tokens.json`，不是本轮重新选色：

| 品牌角色 | 已有值 | 应用原则 |
| --- | --- | --- |
| coral | `#F17561` | 核心品牌识别和已约定的强调 |
| peach | `#FFD0B3` | 低频插图、引导、辅助色面 |
| berry | `#A03259` | 按现有品牌规范作为辅助，不代替错误状态 |
| paper | `#FAF8F4` | 品牌纸色参考；不据此覆盖应用所有实际表面 |
| ink | `#28232A` | 品牌文字参考 |
| action | `#BE4C42` | 品牌动作色参考；最终映射遵循当前产品主题语义 |

品牌色板与实际界面主题不同：Web、Compose、SwiftUI 已有 background / raised / text / accent / brandCoral 等角色，本轮不替换现有浅色与深色底面，也不把品牌色板原样硬编码到各页。应核对当前最终生效主题后，统一映射品牌、主动作、选中、焦点、成功、警告、危险等语义。

Granola 可借鉴的是同一种表面在全产品重复使用、装饰色面积受控、主次动作对比明确。深色主题沿用 Kooyu 的现有方向，另行验证对比度；没有 Granola 深色截图证据，也不需要推导一套绿色深色皮肤。

### 5.4 字体、间距和形状

- **标题**：欢迎/引导等少数叙事标题可以采用可用且授权明确的衬线字体。中文优先验证宋体气质的中文字体，不能依靠英文衬线字体触发不受控中文回退。
- **日常界面**：项目名、会话、设置、模型名和正文使用系统无衬线；代码、路径和日志仍使用等宽字体。不要把长中文回答或设置页全改成衬线。
- **手机建议起点**：正文 16–17sp、辅助说明 13–14sp、页面标题 22–26sp、欢迎标题 28–32sp；正文行高约 1.5–1.65。桌面按阅读密度单独映射，不机械使用同字号。
- **圆角**：行/输入分组约 12–16dp，主输入框约 22–26dp，胶囊用于按钮和少量选择控件。不要把所有卡片、标签、底栏都变成超大胶囊。
- **间距**：用 4/8/12/16/24/32 的统一尺度。相关字段靠近，分组之间留白；不靠每块都描边形成层级。
- **触摸与文字放大**：可见图标可小，触摸区域至少按 Android 48dp / iOS 44pt 验证；工具栏可以滚动或合理换行，不能以缩小点击区域换取一行显示。
- **动效**：优先小幅展开、淡入和状态过渡；停止、审批、错误应及时响应；支持减少动态效果。

## 6. 关键页面的改造要求

### 首页

顶部一行显示品牌、当前电脑、收件箱与新建；当前电脑显示名称和状态，不显示大段内部连接术语。项目采用分组标题与轻量会话行；会话行只保留名称、harness、当前状态及必要时间。项目操作就近展开。

有工作需要处理时，展示一条可点击的摘要，如“2 项等待回答 · 1 项待验收”，点击进入收件箱或工作记录；不要把数字当作新的统计大屏。无项目时给出新建项目/浏览目录入口，不要求先填写多页配置。

### 对话与输入区

输入区继续遵守桌面的配置和发送规则。外观改变不应改变 `idle → new`、其它状态自动排队、停止当前轮、附件上传状态及失败保留草稿等逻辑。

平时只突出输入和发送。harness、权限、模型、思考展示当前值；更复杂的配置进入小面板，不能藏到用户无法判断当前设置。运行摘要可写为“Codex 正在检查测试 · 2 分钟”，点开才看工具轨迹。审批到来时及时显示问题和动作范围，不能被欢迎页或日志顶出可见区。

### 工作记录、成果与计划

先建立一个简洁聚合入口，复用已有目标/成果详情。每个成果能回到所属项目和对话；不要只显示文件路径。验证结果区分实际运行的检查、模型自述和用户验收。

自动计划详情必须明确执行设备、自然语言时刻、时区、下一次执行、上次结果及暂停动作。手动“立即执行”应产生独立运行记录，不能让用户误以为更改了下一次计划。

### 模型来源与设置

模型来源先回答“谁在用什么”，再提供编辑操作。来源状态、发现模型、绑定模型和引擎默认值分层显示。不能把“不支持该能力”伪装成灰色选项却不说明原因，也不能为了简洁丢掉错误修复入口。

设置一级继续显示远程连接；会话托管保留管理入口，但授权和托管的主要触发路径在对话内。用量、模型管理不应再复制到多处产生不一致的编辑入口。

## 7. 实施顺序与验收

1. **统一基础视觉**：保留 Kooyu 品牌色和现有主题方向，建立一致的语义映射到 Web CSS、Compose 和 SwiftUI；先统一文字、主动作、选中态与表面层次，再整理列表、输入框、弹层和设置行。不能只改手机主题，也不能继续在各页写新的硬编码颜色。
2. **整理导航与上下文**：稳定 Host → 项目 → 对话 → 工作/成果的身份关系和返回路径；保留原有首页项目管理与目录选择。通知跳转必须携带真实目标，不按当前 tab 猜测目标。
3. **补工作闭环**：优先复用已有目标、文件、成果和验收能力，增加工作聚合入口与过程摘要；然后补原生端自动计划承接。权限不足、本机专用操作和不支持能力需要清晰说明。
4. **同步三端验证**：桌面、Android 手机/平板分别检查，iOS 在可用 Xcode 环境检查。覆盖浅色、深色、键盘、大字体、长模型名、多项目、离线、等待审批、结果未知和执行失败。

验收重点：

- 进入首页后能迅速找到项目、新建、当前电脑和收件箱；项目不重新独立占一个底部页。
- 用户可以通过主对话创建项目、申请授权和触发托管；设置不成为任务执行的前置步骤。
- 任一工作都能从对话找到过程、成果和验证证据；从成果能回到原始对话。
- 输入配置、队列、停止和审批语义跨端一致；外观统一不以删减移动端功能为代价。
- Kooyu 品牌身份在桌面和移动端一致；轻量层次与留白适配各端密度，运行、等待、错误仍有明确文字及对比度。
- 页面只展示可用能力和真实数据；没有实现的技能市场、手机本地执行等不使用静态卡片冒充。

### 11.2 小功能：优先解决“找不到、看不懂、回不去”

下列是 Kooyu 扩展建议，不声称在 Marvis 截图里逐项看到，也不将已有通用操作重复列为新增。

1. **只看需要我处理的工作。** 首页/工作记录筛选待回答、待审批、待验收；收件箱区分未读通知与尚未处理的请求，读过不代表已解决。双端同一口径。
2. **恢复到离开的位置。** 按会话保留草稿和滚动位置；返回时提供最新消息/首个未读定位。当前已有部分草稿状态，需补齐持久化和边界验证，不能直接承诺跨设备同步草稿。
3. **排队消息可见。** 沿用桌面的自动排队逻辑，手机同样看到排队数量、内容及发送结果；修改、撤销仅在服务端支持时提供，不能本地删除后假装服务端已撤回。
4. **重新连接后的变化提示。** 提示新增回答、待处理请求和新成果，定位到对应内容；基于实际同步事件生成，不将网络重连当作重发输入的触发器。
5. **成果回到来源。** 每张卡有所属会话和相关工作入口；手机便于分享，桌面便于预览或定位文件；不存在或失效的文件说明原因。
6. **从列表直接采取下一步。** 项目行新建对话/浏览目录、工作行继续处理、计划行暂停/查看上次运行，减少进设置绕路。新建和置顶已存在时只优化位置与双端一致性。
7. **筛选与选择记忆。** 保留项目筛选、列表折叠和最近使用的有效配置；模型记忆以 harness、来源、电脑为范围，来源被移除或能力变化时不能继续套用旧模型。
8. **明确失败与结果待核对。** 网络错误时保留输入；危险写操作结果未知时先核对服务端，不能用一个通用重试键制造重复动作；双端统一文案与状态。

不优先增加：3D 办公室、无后端支持的技能商店、独立重复的统计大屏、占据首页的大量功能磁贴。它们对当前跨端工作闭环的帮助低于上述改动。

## 12. 建议的落地批次

| 批次 | 内容 | 可以验证的结果 |
| --- | --- | --- |
| P0：风格与核心操作一致 | 保留品牌色；统一列表、输入、选择器、弹层、问题/审批卡；整理连接与会话上下文 | 同一会话双端配置与状态一致；输入/排队/停止/回答/审批完整；移动端键盘和长文本不遮挡关键动作 |
