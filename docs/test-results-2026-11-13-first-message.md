# 首条消息反馈延迟排查与优化

日期：2026-11-13。所有新建/发送性能测试使用独立测试 Host 和合成发送回执，没有向真实模型发起请求。

## 问题与修复

1. 新对话原先依次等待创建会话、发送确认，再切换到聊天界面；父级操作还会刷新完整快照。首条消息和动画因此一起被延后。现在点击发送就显示用户消息和创建动画，创建成功立即进入本地会话，不再等待发送回执或快照。
2. 原先每次快照都同步扫描全部引擎安装目录、PATH 和启动模式。这会阻塞 Host 事件循环。现在仅对安装健康信息缓存 10 秒；installations.json 元数据变化、PATH/相关环境变化和显式刷新会立即使缓存失效。会话、原生配置文件位置、默认模型和模型列表仍实时读取，实际启动也重新验证入口。
3. 新消息使用与发送命令相同的 requestId，只有相应回执才清理乐观消息。历史分页先于实时事件到达也会去重。创建/发送失败恢复输入；快速连续 Enter 不会重复创建。过期快照不能覆盖刚创建的本地会话。

## 测量

### 页面反馈：受控网络延迟

分别在创建响应、发送响应中注入 1,200 毫秒延迟，总计 2,400 毫秒。

| 场景                          | 用户消息出现 | 加载动画出现 |
| ----------------------------- | -----------: | -----------: |
| 修改前桌面 1440px             |     3,478 ms |     3,481 ms |
| 修改后桌面 1440px（最终复测） |        56 ms |        60 ms |
| 修改后手机 390px（最终复测）  |        47 ms |        50 ms |

阈值为 500 ms。以上衡量的是页面即时反馈，不是模型首字延迟。桌面/手机截图已进行一轮视觉检查，消息和现有加载组件均清晰可见。

### 快照：同一隔离 Host、相同数据

通过清除安装健康缓存模拟原有每次扫描行为；不清除 Windows 注册表扫描本身已有的缓存。

| 请求                 | 耗时                                       |
| -------------------- | ------------------------------------------ |
| 首次冷快照           | 1,717.3 ms                                 |
| 每次重新扫描（4 次） | 357.7 / 322.3 / 274.4 / 315.4 ms           |
| 缓存命中（6 次）     | 11.2 / 12.9 / 11.1 / 14.4 / 13.3 / 16.9 ms |
| health               | 1.2 ms                                     |

同一快照响应均为 15,192 字节。缓存命中中位数 13.1 ms，重新扫描中位数 318.85 ms，约减少 95.9%。冷启动和缓存失效后的扫描仍有开销；这些隔离测试不能当作生产 Host 已生效的数据。修改前对现有 4330 Host 的只读快照采样约为 621–641 ms。

历史会话只读样本还显示，发送受理到原生首次输出约需 5.5–11.6 秒；这些包含引擎启动、配置与原生处理等因素，并非受控的模型测速。本次修复让等待期间及时显示状态，不承诺消除这些真实执行耗时。
